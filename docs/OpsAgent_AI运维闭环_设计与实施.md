# OpsAgent AI 运维闭环设计

## 问题归纳

改进清单揭示三个核心问题：导航按技术模块堆叠，监控与服务关系分离；AI 主要围绕文档回答，运行数据和模型选择没有贯通；发现问题之后缺少可重复、可验证的处置流程。索引失败任务未区分文档生命周期，导致无效修复入口。页面大标题、重复介绍卡片和部分固定尺寸降低了信息密度。

## 本轮信息架构

主线：发现风险 → AI 诊断 → 处置与协作 → 验证与沉淀。

- 运行总览：当下的任务、风险和下一步；保留能力搜索，压缩介绍空间。
- 运维中心：运行态势、服务与拓扑、治理信息、工作流。旧监控与目录链接保留重定向。
- AI 诊断：私有会话、真实运行上下文、知识引用、已配置模型选择。
- 工单处置：完整的任务查询、分派、状态机、处置记录。它与总览的摘要职责不同，应保留。
- 协作与知识：SLA、值班、知识库及管理员维护入口。

## 能力边界与实现要求

保留现有 Spring Cloud 微服务。平台服务聚合 Prometheus、Nacos、Sentinel 和 CMDB，RAG 仅获取脱敏白名单数据，所有运行信息带来源与采集时间。模型已配置与实时可连通分别表达；明确选择的模型失败时不暗中切换。

趋势预警采用真实时间序列的可解释外推，公开样本量、窗口、预测区间与局限，缺数据就是未知。不能把统计预测写成 AI 能准确预知故障。

处置采用固定步骤和审计记录。首先实现只读巡检与独立容器的服务不可用演练：注入健康故障、检测、固定恢复、二次验证。演练容器不公开端口、不接 Docker socket、不影响业务容器。生产服务不接受模型生成的任意命令。本轮不增加 Kubernetes。

公网管理员保持强密码。可选 user/user 访客入口通过验证码获取独立临时身份，业务只读、允许自己的 AI 会话，不能执行管理和处置操作；正常账号历史不受影响。AI 仍受现有全局预算保护。

## 界面原则

沿用蓝白渐变、统一字体和控件体系，修改组件与所属样式源，不堆叠总 CSS 覆盖。页面标题压缩成工具栏，业务内容置于首屏。登录默认轮播，移除演示标签和暂停按钮；遵循减少动态效果偏好。小屏按内容重排，必要的纵向滚动保留，表格横向滚动限制在表格容器内。

## 验证与部署

权限、模型路由、运行数据缺失、索引生命周期、工作流故障恢复做有意义的测试；执行 Maven clean verify、前端构建与关键浏览器交互检查。云端先备份，只应用增量结构与镜像，不重新导入本机业务数据。公网验证登录、受限访客、数据采集、问答完整性与演练恢复后交付。
